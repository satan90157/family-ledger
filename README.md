## v1.8.5 — 自動分類規則與歷史交易批次分類

### 重要：這次前端與後端都需要更新

**只更新 `index.html` 不夠。** 這版新增 Google Sheets `CategoryRules` 工作表與兩個後端操作，需要新版 Apps Script。

1. **先備份**：在電腦下載目前完整 JSON，並在 Google Drive 複製一份主 Google Sheets。
2. 在原本的 Apps Script 專案，完整替換 `Code.gs`；**新增** `CategoryRules.gs`（使用壓縮檔 `apps-script/CategoryRules.gs`）。原本的 `Auth.gs` 和 `Budget.gs` 沿用即可。
3. Apps Script →「部署」→「管理部署作業」→選原部署的鉛筆圖示 → 選「新版本」→「部署」。**不要建立新的部署，也不用重跑 `setupV17()`。** 原 `/exec` 網址保持不變。
4. GitHub Pages 原位置只替換 `index.html`，等網站更新後電腦強制重新整理、iPhone 關閉主畫面 App 再開。底部應顯示 `v1.8.5`。
5. 到「同步設定 → 自動分類規則」，用「優食台灣」→「包含」→「餐飲」→「家庭共用」建立第一條規則。成功後 Google Sheets 會自動建立 `CategoryRules` 工作表，其他裝置登入會自動下載。
6. 再建立「富胖達」→「餐飲」。新匯入的 Invoice CSV 會套用規則；已存在的發票不會因重新匯入而被改動。
7. 在「收支明細」搜尋「優食台灣」，下方「批次修改交易分類」選「餐飲」與「僅其他支出」，先按「預覽影響範圍」查看筆數、金額和年度，確認後才按「確認批次修改」。

### 分類優先順序與安全保護

- 僅新匯入的發票會自動套用規則；先比對「名稱完全相同」，再比對「包含」；多條同時符合時優先採用關鍵字較長者。
- 「只有我自己」規則僅授權給建立者，且只會套用到歸屬該使用者的發票；家庭規則可供兩人共用。
- 當使用者在記帳表單修改分類時，保存 `_categoryManual=true`，未來自動分類不會覆蓋。過去舊版資料沒有這個欄位，**無法事後百分之百區分人工分類與系統分類**；批次修改請優先選擇「僅其他支出」，並預覽確認。
- 批次修改只影響**已下載到目前瀏覽器、且符合上方搜尋篩選條件**的支出紀錄；只改分類與手動標記，不改動 ID、日期、店家、發票號碼、交易金額。
- 批次修改仍透過原本的 `delta` 逐批同步，有版本衝突時不會覆蓋雲端；仍需在同步完成、待同步數為 0 後再換裝置。
- 修改或刪除分類規則不追溯改動歷史交易。規則在 `CategoryRules` 獨立保存，修改採 `_rev` 版本檢查，並留下 `AuditLog`；刪除是停用而非刪除交易。
- 建立或修改規則前需要成功從新版後端下載規則，避免沒有讀到其他裝置既有規則而產生重複。

**驗證狀態**：已完成 JavaScript 靜態語法與結構檢查；無你正式 Google Sheets 的端對端測試，第一次請先用少量發票、單條規則驗證。

## v1.8.4 — 自訂分類完整核對與安全補上傳

## 這版修復的情況

電腦在舊版（例如 v1.5／v1.7）新增了 12 個自訂分類，但 Google Sheets 實際只有 3 個、手機也只看到 3 個；舊分類因為未被標記為待同步，電腦可能誤以為已同步。

## 升級與實際操作

1. 如已經使用 v1.8 的 Apps Script，只需替換 GitHub Pages 根目錄的 `index.html`；`Code.gs`、`Auth.gs`、`Budget.gs` 與 `/exec` 網址**不用變**。
2. **先在保有 12 個分類的電腦**開啟 v1.8.4。不要清除快取、登出或刪除舊分類。
3. 到「同步設定 → 自訂分類完整核對／修復」，按「① 核對本機與雲端分類」。程式會查詢所有有紀錄的年度，分類會分為「雲端缺少」「已同步」「雲端同名、不同 ID」「同 ID 內容不同」「雲端已刪除」。
4. 點「② 下載本機完整備份」，確認 JSON 已出現在電腦的下載資料夾。
5. 勾選真正缺少的分類，按「③ 上傳勾選的缺少分類」。此操作僅針對 `source=category-definition` 的新增紀錄，沒有修改任何發票、交易金額或現有雲端分類。
6. 等畫面顯示成功新增的數量，再使用 iPhone 開啟新版，按「立即讀取雲端」。預期手機會補齊雲端所有同年度分類。
7. 可回到 Google Sheets 的 `Records_2026` 篩選 `Source=category-definition` 核對結果；建議重新執行一次完整核對。

**額外防護**：平常下載選定年度時，如果偵測到本機有該年度的自訂分類 ID 不在雲端且尚未待同步，頂端會顯示橘色提醒，不再誤顯示一切完成。完整核對後送出前會再次下載資料確認，避免重複名稱或 ID；如果雲端出現版本衝突，後端拒絕覆蓋並保留未解決內容。

**重要限制**：同名不同 ID、同 ID 內容不同以及雲端已刪除的分類不會自動覆蓋或消除，需另行人工確認。此版已做靜態語法檢查，但尚未在你正式的 Google Sheets 實測。

## v1.8.3 — 同一張發票逐筆解決跨裝置衝突

## v1.8.3 新增（從 v1.8.2 更新只需替換 index.html）

- 收支交易的同一 ID（包含同一張雲端發票）被電腦與手機各自修改時，顯示「跨裝置資料衝突」，**不直接決定哪邊正確**。
- 在遇到衝突的裝置上，先下載 JSON 備份 → 點「比較交易差異」，會並排顯示本機與 Google Sheets 的日期、店家、總金額、分類、歸屬、備註、發票號碼及差異欄位。
- 每筆可選「採用本機」「採用雲端」「暫不處理」。**只有分類不同**時，採用本機只會修改雲端的分類，保留其他雲端欄位。其他情況選擇的是整筆交易的版本。
- 採用本機時，使用目前雲端 `_rev` 向原本 `delta` 後端提交，因此會經過並行版本驗證且成功後寫入 `AuditLog`；採用雲端時只更新本機，不會重複新增一筆消費。
- 比較後若任一選定交易又在本機或雲端被改動，會停止該批操作，請重新比較，避免覆蓋新修改。
- 1.8.2 的自訂分類雙向合併仍在，**分類衝突與交易衝突是兩個分開的操作**。

### 直接更新／測試方式

1. 請先分別在電腦與手機下載 JSON 備份；確認兩台連到**同一個** Google Sheets。
2. GitHub Pages 只替換壓縮檔內的 `index.html`，原 `Code.gs`、`Auth.gs`、`Budget.gs` 與 `/exec` 網址都不必更新（前提是已使用 v1.8 後端）。
3. 待 GitHub Pages 發布後，電腦強制重新整理，iPhone 從 App 切換器關掉主畫面 Web App 再開；底部應顯示 **v1.8.3**。
4. 先在電腦改一張發票的分類，確認同步成功；手機在同步前若已對同一張發票做不同分類修改，就會看到衝突。從產生衝突的裝置按「下載本機 JSON 備份」→「比較交易差異」，逐筆選擇後按「套用逐筆選擇」。
5. 成功後重新整理兩台，核對同一張發票只出現一次、分類相同、金額未變，並檢查 `AuditLog`。若仍有其他衝突，請再次備份、再比較。

**目前限制**：若兩台原本使用相同 ID 但 `_rev` 也相同，內容卻不同，既有的「資料版本有差異」警示仍不會自動進入這個衝突處理畫面；這類舊資料請先備份後再診斷。本版已完成程式語法檢查，但尚未連你的正式 Google Sheets 做端到端測試。

## v1.8.2 自訂分類雙向合併（保留）

- 手機遇到 `版本衝突` 時，直接列出衝突項目及本機分類名稱。
- **先下載手機端完整 JSON 備份**，再由使用者確認「雙向合併分類」。
- 同一 ID 的自訂分類若內容相同則去重；若兩邊分類名稱不同，保留雲端原 ID，手機獨有分類會產生新 ID 並等待上傳。
- 從雲端下載所有未衝突的獨立 ID；不會刪除或覆蓋一般交易（同一筆支出／收入有版本衝突時需另外確認）。
- 若在查詢期間本機紀錄又被編輯，該筆仍會保留，不會被覆蓋。
- 發生版本衝突後停止自動重送同一批資料，直到使用者處理完成。

**操作提醒**：先確認電腦與手機連線到同一份 Apps Script／Google Sheets，再合併。若分類之外的交易也有衝突，這版不會擅自選一邊，需另外處理。尚未在使用者實際環境完成端對端測試。

## 本次修正

- 頁首常駐 Google Sheets 同步狀態：橘色表示尚未同步／讀取中，綠色表示已收到後端確認，紅色表示同步失敗、版本衝突或本機與雲端資料有差異。
- 新增／修改／刪除交易一律先保留在本機待同步清單，只有收到後端確認版本號，才顯示雲端同步完成。

- 同步下載時，如果發現相同 `_rev` 的本機和雲端交易內容不一致，先保留本機值並以紅色警示，避免靜默覆蓋以前改好的分類。**此警示需要人手確認資料、備份後再處理。**

## Apps Script 部署（必要）

1. 在現有 Apps Script 專案，把 `apps-script/Code.gs` **完整替換**舊檔，再新增一個 Apps Script 檔案 `Auth.gs`，貼入 `apps-script/Auth.gs`。
2. 確認 Script Properties：

   - `SPREADSHEET_ID`：原本主 Google Sheets 的 ID（沿用）。
   - `ACCESS_TOKEN`：原本至少 24 字元的隨機密鑰（沿用；現在只在後端簽署登入憑證）。
   - `BOOTSTRAP_ME_PASSWORD`：承瑋初始密碼，至少 6 個字元（建議混合英文字母與數字）。

   - `BACKUP_SPREADSHEET_ID`：另一份私人備份 Google Sheets 的 ID（建議設定）。

3. 在 Apps Script 編輯器手動執行 **`setupV17()`** 一次，核准所需權限。此函式會建立 `Users`、`AuditLog`、年度工作表，儲存加鹽雜湊後**刪除 Script Properties 中的兩組明文初始密碼**。確認成功後不要再執行第二次。

5. 「部署 → 管理部署作業 → 編輯 → 新版本 → 部署」，執行身分選「我」，存取權按原設定「任何人」。原網站前端必須先通過個人登入，後端才允許讀寫。
6. 將 v1.7 的 `index.html` 替換 GitHub Pages 倉庫根目錄同名檔案。
7. 在 iPhone 或電腦開啟網頁，輸入 Apps Script `/exec` 網址、選擇使用者及密碼登入。第一次仍須提供網址，但不用再輸入舊 Token；後續同一瀏覽器會保存網址。

## 功能與限制

- 兩個帳號：承瑋（me）、俐穎（wife）；兩人能查看及編輯家庭交易。後端按**實際登入者**記錄新增、修改、刪除，不能透過前端指定操作者。
- 登入憑證有效 12 小時，儲存在該瀏覽器的 `sessionStorage`；登出清除憑證，且在沒有待同步修改時清除本機記帳快取。手機加入主畫面的獨立 Web App 可能需要重新登入。
- 密碼只經由 HTTPS POST 傳至 Apps Script 後端，後端存加鹽、多輪 SHA-256 雜湊；Google Sheets 的 `Users` 是私人資料表。這是家庭自用的輕量驗證，**不是銀行等級安全機制**；請使用強且不重複的密碼。
- 為了家庭使用便利性，初始化允許 6 字元密碼；純 6 位數只有 100 萬種可能，安全性明顯弱於較長密碼，請至少避免生日、電話末六碼及其他網站重複使用的密碼。
- 資料寫入 `Records_YYYY`；登入預設只向雲端讀取本年度，可按「載入年度」再抓舊年份。既有瀏覽器快取可能包含之前載入的年份，因此不代表它們重新從伺服器下載。
- `AuditLog` 保留時間、登入帳號、操作、交易 ID、修改前及修改後 JSON；網站的「操作紀錄」顯示最近 100 筆摘要。
- 既有交易**暫不支援直接變更年份**（需在未來版本加入跨年度移動與稽核）。如需修改既有交易年份，應先另行備份再處理。
- 不提供自行註冊、忘記密碼重設、細緻權限角色；密碼修改須由 Sheets 管理者在後端以安全流程操作（本版沒有前端修改密碼）。
- 由於 Apps Script 是無狀態 Web App，會把有時效的簽章憑證送在讀取網址參數；請勿分享帶有 `session` 參數的 URL，亦勿在不可信任的裝置上登入。
